### 1.2 实际流程（静态代码）

1. `Exploration.unity` 加载 → `GameBootstrap.Awake` 创建 `GameManager`。
2. `GameManager.Start` → `BuildWorld()` 按以下顺序组装（`GameManager.cs:~50-160`）：地形 → 水面 → 天空 → 日月光 → `DayNightCycle` → 玩家（`PlayerCharacter`）→ 相机（`CameraRig`）→ `WorldBuilder`（物件/敌人）→ `TouchControls` → `GameHUD` → **Phase 1**（`EchoManager` + `SquadManager.Init`）→ **v2.0**（`EchoSystem` + `TeamManager.Initialize` + `Recalc` + `GrantStarterIfEmpty`）→ 面板（`TeamPanel`、`EchoPanel`、`ResonanceHUD`）→ `SaveSystem.LoadInto`。
3. 每帧输入路由（`GameManager.Update`，`GameManager.cs:182-187`）：
   - `ConsumeAttack()` → `Player.OnAttackPressed()`（普攻）
   - `ConsumeDodge()` → `Player.Dodge()`（闪避）
   - `ConsumeSkill()` → `Player.UseSkill()` → `TeamManager.UseSkill()`（E）
   - `ConsumeBurst()` → `Player.TryBurst()` → `TeamManager.UseBurst()`（Q）
   - Esc 暂停、Tab 地图、F5 保存同在 `Update`。
4. 战斗本体：**单操作体**。所有角色共用同一个 `PlayerCharacter`（一套物理与输入）；切换只换外观（`ResonatorVisuals.Build` 的几何体 rig）与数值（`TeamManager.ApplyActive`）。
5. 死亡：`PlayerCharacter.Die()`（`PlayerCharacter.cs:~777-782`）不设游戏结束——回满 HP/体力，`GameManager.OnPlayerDied()`（`GameManager.cs:~215`）传回出生点、清护盾。**无 Game Over 流程**。

## 5. 弹反系统及其判定实现

### 5.1 结论先行：弹反不存在

全工程 `.cs` 文件 grep `parry|弹反|格挡|招架|perfect.*block`：**零命中**。弹反（C-03）没有任何代码、没有判定窗口、没有成功/失败分支、没有反馈、没有惩罚。

### 5.2 最接近的现有机制：完美闪避反击（不是弹反）

| 文件 | 内容 |
|---|---|
| `Assets/Scripts/Phase1/SquadManager.cs:358-375` | `CheckPerfectDodge()`：闪避启动瞬间，若 5m 内有敌人 `IsWindingUp`，则该敌人受 40 伤害 + 0.35s 慢动作（`SlowMoRoutine`，`timeScale 0.3`），Toast“完美闪避 · 反击” |
| `Assets/Scripts/Phase1/SquadManager.cs:193-195` | 触发点：`Update` 每帧检测 `Dodging` 由 false 变 true 的边缘 |
| `Assets/TideSong/Scripts/Enemies/EnemyAI.cs:24` | `IsWindingUp` 暴露前摇状态（为完美闪避而设） |

与弹反的区别（设计层面，须由 C-03 决定）：完美闪避是**闪避动作的奖励判定**（发生在玩家闪避启动时）；弹反通常是**防御/格挡动作在攻击命中瞬间的判定**（需要独立的格挡输入、判定窗口、成功反制与失败惩罚）。两者输入、时机、反馈均不同，不能把完美闪避改名充当弹反。

### 8.4 抽卡战斗公式与实时战斗的关系：**无连接**

- 抽卡公式 `GachaCombatDamageCalculator`（`Assets/Scripts/Gacha/Consolidated/GachaCombatDamageCalculator.cs`）：`D = attack × baseMultiplier × bonusMultiplier × 100/(100+defense) × crit × (1−reduction)`，与冻结公式 `D = A×M×B×100/(100+DEF)×C×(1−R)` 一致（防御公式仍标注“暂用”，待最终确定）。
- 该类仅被 `GachaCombatActionResolver.cs` 引用；**抽卡系统与 TideSong/Phase1 实时战斗双向零引用**（grep `TideSong` 于 `Scripts/Gacha/`、grep `Gacha` 于 `TideSong/` 均为空）。
- 实时战斗伤害公式（`CombatUtil.DealDamage`）：`baseDmg × AttackMultiplier × (1+属性加成) × 套装加成 × 暴击 × (1+易伤)`，**无防御减免**（敌人无 DEF 字段）、**无技能倍率乘区之外的独立乘区**。两套公式是平行系统，数值口径不同（抽卡用 `GachaFinalCombatStats` 快照，实时用 `EchoSystem` 百分点汇总）。

## 14. 推荐实施顺序

Karen 派发的顺序是 C-02 → C-03 → C-04 → C-05 → C-06。本审计建议**保留该顺序，但把 C-04 与 C-05 对调**，理由如下（最终是否对调由 Karen 确认）：

1. **先定 5 个阻塞决定，再开 C-02**：1–4 键归属、R 键归属、SP 去留、能量池统一、AI 挂哪套队伍（§11-1/2/7/8）。C-02 的 AI 技能写在哪套队伍上，取决于第 1 条；不等决定就开工会在错误的地基上写代码。
2. **C-02 AI 队友技能释放**：在已验证的 `SquadCompanion` 跟随/普攻 AI 上加技能决策（时机/目标/消耗/冷却/防重复释放）。
3. **C-03 弹反机制完整化**：复用 `IsWindingUp` 与前摇（0.65s）做判定窗口；与完美闪避的关系须在设计中明确（并存/合并/取代）。
4. **C-05 属性差异化退场技**（建议提前）：C-05 的属性映射表是 C-04 机制设计的输入之一（支援位特殊机制很可能与属性挂钩）；且 C-05 已有 Phase 1 入场技的现成范式，工作量小于 C-04。
5. **C-04 第四支援位特殊机制**（建议延后）：目前代码零基础、设计零基础，必须先有机制设计文档才能开工；放在 C-05 之后可复用属性映射结论。
6. **C-06 战斗整合验收**：最后。含新增 v2.0 smoke 模式、弹反测试、AI 技能测试、多角色组合、连续战斗；Play Mode 部分必须在用户机器上点验，沙箱只能做静态与构建检查。

> 顺序变更提示：以上第 4、5 条的对调建议**不是决定**，按 Karen 纪律“不把设计建议擅自变成正式规则”，是否对调等 Karen 在检查本报告后定。
